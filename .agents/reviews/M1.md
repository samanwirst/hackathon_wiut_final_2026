## Findings

### 1. M1-006 — P1 — Webhook path authorization bypass

- File and line: `services/api/app/actions.py:113`.
- Reproduction: Allowlist `http://127.0.0.1:9876/hook/`; execute a webhook to `/hook/../admin`.
- Expected behavior: Reject delivery outside `/hook/`.
- Actual behavior: Authorization accepts it; HTTPX delivers `/admin`. The observed transport URL was `http://127.0.0.1:9876/admin`, and the action reported done.
- Minimal suggested fix: Authorize/send one canonical URL; reject ambiguous traversal encodings and enforce the prefix on the normalized path.

### 2. M1-003 — P1 — Disable does not revoke remaining events in a frame

- File and line: `services/api/app/pipeline.py:240`.
- Reproduction: Two tracked cars emit enter events together. Pause after the first action commits, disable through the API, then resume.
- Expected behavior: Only the first event/action remains.
- Actual behavior: Disable returned 200 with enabled=false; event count subsequently increased from one to two and both notifications completed.
- Minimal suggested fix: Recheck authoritative approval for every event before persistence/dispatch and cover this batch interleaving. The previous fix is incomplete.

### 3. M1-007 — P1 — Retry permanently skips an undispatched action

- File and line: `services/api/app/pipeline.py:248`; event commit at line 266.
- Reproduction: Interrupt immediately before action execution, recover the processing source, and replay identical input.
- Expected behavior: Complete the pending action without duplicating completed actions.
- Actual behavior: Source becomes processed, but the event remains pending with zero execution rows and no notification.
- Minimal suggested fix: Recover undispatched pending events, preserve completed-event deduplication, and persist local action/status changes atomically with stable webhook dispatch identity.

### 4. M1-008 — P1 — Invalid action config leaves a source stuck

- File and line: `services/api/app/schemas.py:50`; `services/api/app/pipeline.py:286`.
- Reproduction: Create/enable a notification with `config.title={"invalid":"object"}` and process a valid MP4.
- Expected behavior: Return 422 for invalid configuration; database failures leave a visible, retryable failed source.
- Actual behavior: SQLite rejects the dict during commit. Failure recording lacks rollback and is swallowed: status=processing, error=null, worker absent, retry=409.
- Minimal suggested fix: Validate the notification title type/length and roll back failed transactions before persisting failure.

### 5. M1-009 — P2 — Evidence-write failure is silently ignored

- File and line: `services/api/app/pipeline.py:177`.
- Reproduction: Inject `cv2.imwrite=False` for event evidence.
- Expected behavior: Surface persistence failure and avoid a nonexistent evidence URL.
- Actual behavior: Source=processed and action=done, while evidence returns 404.
- Minimal suggested fix: Check the write result, raise a clear error, and roll back incomplete event work. This is a deferrable fault-handling risk.
