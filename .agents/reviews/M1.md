## Findings

### 1. M1-001 — Webhook prefix check permits an internal destination

- Severity: **P1**.
- File and line: `services/api/app/actions.py:26`.
- Reproduction: allow `http://approved.example`, then execute `http://approved.example@127.0.0.1:9876/private`. HTTPX MockTransport observed host `127.0.0.1`, port `9876`, path `/private`; action status became `done`.
- Expected behavior: authorization follows the actual parsed destination and excludes unintended internal services.
- Actual behavior: `startswith` approves a string whose allowed hostname is actually userinfo. Empty allowlist remains safe, but configuring a hostname prefix exposes the bypass.
- Minimal suggested fix: canonical URL parsing, userinfo rejection, exact scheme/host/port comparison, separate path restrictions, and internal-address checks at connection time.

### 2. M1-002 — Subsequent count episodes are silently discarded

- Severity: **P1**.
- File and line: `packages/vision/visionflow_vision/events.py:133`; persistence filter at `services/api/app/pipeline.py:182`.
- Reproduction: two cars inside, outside, then inside again; threshold 1, cooldown 0. Engine emitted two events with the same `object_count_exceeded:None:visit0` key; only one event and notification persisted.
- Expected behavior: rising-edge behavior rearms after count drops, giving each distinct episode an idempotent identity.
- Actual behavior: aggregate events never advance a visit counter; all later episodes collide with the first database row.
- Minimal suggested fix: deterministic aggregate episode counter in the key, with persistence/action tests covering repeated crossings and replay.

### 3. M1-003 — Disable does not revoke an active worker

- Severity: **P1**.
- File and line: `services/api/app/pipeline.py:180`; action call at line 206.
- Reproduction: pause before the first detector result, disable the enabled workflow successfully, then resume. The worker persisted an enter event and successful notification after disable.
- Expected behavior: subsequent actions stop once workflow authorization is revoked.
- Actual behavior: the enabled workflow list is loaded once and retained; later database changes are ignored.
- Minimal suggested fix: fresh authoritative enabled-state checks before event acceptance/action execution, coordinated with disable. Do not rely on the cached ORM object.

### 4. M1-004 — Concurrent videos share persistent tracker state

- Severity: **P1**.
- File and line: `services/api/app/pipeline.py:160`; singleton returned at line 51.
- Reproduction: pause video A after its first two detections; run video B through the shared detector's reset; resume A. The stateful test double changed A's IDs from `[1,1]` to `2`, producing two enter events and notifications for one stationary object.
- Expected behavior: tracker state belongs to one source/session.
- Actual behavior: per-source threads reset and use a shared detector; the construction lock does not protect processing sessions. The production wrapper also holds persistent ByteTrack state and resets its predictor between sessions.
- Minimal suggested fix: serialize entire detector sessions for M1, or allocate independent tracker instances per source. A per-frame mutex alone is insufficient.

### 5. M1-005 — Interrupted processing remains permanently stuck

- Severity: **P1**.
- File and line: `services/api/app/main.py:170`; startup at line 45.
- Reproduction: retain a persisted `processing` row without a live worker, execute startup's `init_db`, then request processing. Response remains 409, `source is already being processed`; status remains `processing`.
- Expected behavior: restart identifies interrupted work, exposes the interruption, and allows retry.
- Actual behavior: startup leaves stale status unchanged and the endpoint rejects it indefinitely.
- Minimal suggested fix: recover interrupted rows during single-worker startup. Use ownership/leases if multiple workers are supported.
